# 自动更新与升级备份

本实现以 Sub2API 官方 main `25608d216bb7be04e4a646830cb065cd09b7d7e9` 为更新流程基线。官方响应处理和 `/system/update`、`/system/restart` 两阶段入口继续使用；更新依次检查发布、下载、校验、解包、同文件系统原子替换，再由管理员重启。IKUN2api 的发布签名、兼容检查、数据库与配置快照、失败恢复继续保留。

## 容器版本选择

- `--version` 输出稳定的版本、提交和构建时间，不再带调用时刻的日志前缀。
- 容器入口保留官方的权限修正、参数补全和 `exec`，持久程序选择交给 `--prepare-runtime`。
- 运行程序保存在 `/app/data/runtime/ikun2api`。该数据卷必须保留。
- 直接读取已安装程序的语义版本；不再把 `.image-version` 中的历史日志当成版本来源。
- 已安装版本高于或等于镜像版本时，保留已安装程序，包括同版本不同提交的情况。
- 镜像版本更高时，共用网页更新的兼容检查、备份程序、恢复记录和原子替换步骤。
- 镜像升级被拒绝且原程序摘要未变时，记录失败并继续启动原程序。无法识别的程序不会被静默覆盖。
- 存在待恢复的升级记录时，交给已有 supervisor 处理，不再重复选择镜像。

`IKUN_VERSION` 仍选择 Compose 使用的镜像。后台更新后的程序独立保存在数据卷内，旧镜像版本不会再自动覆盖它，无需每次网页更新后手改 `.env`。

**首次应用本修复需要更新容器镜像。** 旧镜像中的入口脚本不会随网页下载的程序更新。部署时应沿用原 Compose 项目、数据卷和数据库，仅更新应用镜像；不能删除数据卷。systemd 部署继续使用原有的持久程序路径和 supervisor。

## 备份保留

管理员打开“版本与更新”，可设置“自动清理旧备份”和“保留份数”。默认开启，保留 3 份，可选 1–30 份。配置保存在程序旁 `upgrade-backups/policy.json`，容器重建后随数据卷保留。

服务成功启动并完成 supervisor 确认后尝试清理，之后每小时补查。保存设置也触发一次后台清理。

- 每份新备份保存独立的旧程序和版本、摘要记录，数据库及配置仍由现有快照流程保存。
- 按时间戳目录排序保留最近的有效快照；清理前检查数据库和备份程序摘要。
- 存在任何升级/恢复记录时暂停全部清理。
- 缺少完成标记、摘要损坏、名称无法识别的目录保留，不计入有效保留份数。
- 已有旧备份使用时间戳目录、`COMPLETE`、数据库摘要和资料目录识别兼容；不要求旧目录具备新增的程序清单。
- 不清理迁入备份、管理员手工备份、其他目录或符号链接目标。备份根目录是符号链接时拒绝清理。
- 配置读取失败时停止清理；清理失败仅写运维日志，不影响服务启动，也不触发数据库回退。

## 验证范围

回归覆盖容器启动选择、旧日志格式、相同版本、旧镜像、新镜像、升级兼容检查失败、未知版本、升级恢复记录、默认与自定义保留份数、关闭清理、损坏与未完成备份、符号链接、管理员参数校验以及前端保存交互。

本地 Linux 可执行文件回归与真实 Docker 容器重建验收分别记录，不能将前者当成后者。发布前仍通过既有隔离 Compose 迁入演练验证数据保留。
